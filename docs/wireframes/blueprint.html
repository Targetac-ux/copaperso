01 · Decisiones

Base de datos y deploy

Tus dos preguntas, respondidas: Supabase sí, y el backend Node del plan se convierte en las rutas de servidor de un solo proyecto.

Base de datos · Supabase (PostgreSQL)

El modelo es relacional de arriba a abajo, y Supabase además trae Auth para el login del host, Storage para las fotos del Tier List, Realtime para la vista pública en vivo —que entra al MVP— y RLS para separar lo público de lo administrativo. Cuatro problemas del plan resueltos sin infraestructura extra.

App · Nuxt 4 (Vue 3 + TypeScript)

Un solo repo en vez de un frontend Vue y un backend Node separados. Las rutas server/api/* son el backend: ahí viven las reglas de LP, los costos y el log. El navegador nunca escribe directo a la base.

Deploy · Vercel + GitHub

Push a main despliega producción; cada PR genera un preview contra un Supabase de staging. Migraciones versionadas en el repo, nunca cambios a mano en el panel.

Alternativa si prefieres Vue puro

Vite SPA + Supabase Edge Functions (Deno) para las reglas del servidor. Funciona, pero son dos entornos de despliegue, dos lenguajes de runtime y peor SEO en la Home pública.

02 · Revisión

Seis cosas que corregir antes de escribir código

El plan está sólido y muy completo. Estos son los puntos donde, tal como está escrito, el sistema no podría funcionar o se contradice.

CRÍTICO

PARTICIPATION mezcla periodo y sesión

§3 le pone period_id y session_id a la vez. Si la participación es por sesión, el LP se reinicia en cada CopaPerso y el roster mensual de §29 no se puede calcular. Si es por periodo, no hay dónde guardar quién está disponible esta noche.

→ Dos entidades: participation (por mes, con el LP) + session_participant (la banca de esa noche).
CRÍTICO

El LP como contador suelto rompe el "deshacer"

§21 exige poder deshacer acciones importantes, pero si current_lp es un número que se suma y se resta, un undo mal aplicado lo corrompe en silencio y nadie se entera hasta el cierre del mes.

→ lp_event es la fuente de verdad; current_lp es una caché recalculable (100 + suma de deltas vivos).
RESUELTO

Los costos vigentes son los de §13

El wireframe traía otros valores (cambio de Team 500 en vez de 150, Blue Shell 1000 en vez de 500). Manda el plan: cupo 200, cambio de Team 150, sacar de banca 200, cambio de rol y reingreso 300, sacar del cementerio 300, Blue Shell 500. Los subs no tienen tipo de cambio: 1 sub NA/EUW o 2 LATAM valen cualquier recompensa, y lo decide el streamer.

→ Aun así viven en un catálogo editable y versionado por periodo: subir un precio no reescribe lo ya cobrado.
FALTA

winner_team_id no cubre la doble derrota

El Blue Shell (§16) puede dejar con derrota a un jugador del equipo que ganó, y no hay forma de anular una partida mal registrada.

→ El resultado real vive por jugador (win / loss / double_loss); el ganador del equipo queda como dato de conveniencia.
FALTA

PERIOD no existe como entidad

Está implícito en §5 y §29 —todo el reinicio mensual depende de él— pero nunca se declara.

→ Entidad propia con estado, para poder cerrar un mes y congelar su roster.
DECISIÓN

Las recompensas no ejecutan nada: el host mueve a mano

Es la decisión que más simplifica el sistema. No hay motor que valide saldo, cobre y mueva jugadores: el catálogo es una lista de precios de consulta y el host cumple la recompensa arrastrando, asignando o haciendo swap con las herramientas de siempre.

→ Se cae toda una capa de lógica: la "negociación" pasa a ser una bitácora de lo reclamado, y cada movimiento real ya es deshacible como cualquier otro.
RESUELTO

Cárcel, cementerio, cupo y reingreso son cuatro cosas distintas

Cementerio: no alcanzó a inscribirse, con el draft ya arrancado (300 para salir). Cupo: con los equipos ya hechos, alguien del cementerio entra en lugar de un jugador ya seleccionado y se salta el aleatorio (200); el desplazado vuelve a la banca. Rol y reingreso: ya salió sorteado y quiere otro rol (300). Cárcel: el castigo manual del host, tal cual §17.

→ Cementerio y cárcel son estados del participante; cupo y reingreso son recompensas que el host cumple moviendo gente.

Nueve fases, y cómo se cierra cada una

Una fase no está terminada porque "ya se ve bien": está terminada cuando pasan sus pruebas. Vitest para las reglas, Playwright para los flujos del host, y un guion manual antes de cerrar.
